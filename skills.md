# skills.md - how Picky was built

> **The reusable skill** is in `skill/ab-test-decision/SKILL.md`: the method in this journey (plan a test, check a results file, decide with pre-registered rules, report honestly) packaged so any AI assistant can use it. It was tested against a no-skill baseline on five realistic requests (see the end of this file).

**Problem:** PS05 Agent A/B Testing & Auto-Rollout, applied to VANI, IndiaMART's buyer-side voice assistant (a buyer calls a seller, the seller is unavailable, the call is redirected to VANI). **Team build tool:** Claude Code (an AI pair programmer) for design, code, tests and docs; the team directed scope and made the product decisions. **Platform:** Sarvam Saaras (speech-to-text), Sarvam-105B (tagging, optional edit drafting), Bulbul (voices); every paid step is opt-in, budget-capped and costed (`python -m canary fix costs`).

## Journey
1. **Read everything first.** PS05 and PS01, the deck's scoring slides; measured the 713 recordings with code. No labels, transcripts or prompt were provided at first, so every claim had to survive that.
2. **Statistics first.** Lan-DeMets alpha-spending boundaries by recursive integration, checked against published values and a 200,000-run simulation before anything was built on top. One decision function (`Monitor.look`) serves the live engine, the scenarios and the proof lab.
3. **Proof lab and honesty.** Simulated Picky against naive peeking, a fixed-horizon test and "higher rate wins" on identical data. It found our false-win rate slightly above nominal in small slices and a weak broken-test check at a 45% baseline (a 35% silent loss shipped 44% of the time); both are reported, and the second was fixed with a per-arm assigned-vs-logged check (0% shipped).
4. **Labels without a labeller.** Sarvam transcribed and tagged 299 real recordings under a spend cap; a person spot-checks about 40. Local code scans the transcripts for loops with no model, as an independent check on the tagger.
5. **The real prompt arrived, and we corrected ourselves.** VANI's real prompt and IndiaMART's quality matrix contradicted four of our assumptions (the call is inbound, there is no timeline, reading values back is forbidden, live-seller connection is the top priority). We rebuilt the label schema, retired a "failure" our tagger invented, marked results made on our stand-in prompt as stale, and withdrew a claim that rested on that mistake. Nothing was hidden.
6. **The fix loop (the PM's idea) on the real prompt.** A prompt lint finds contradictory ask limits (buyer name 2 vs 3, product 4 vs 5, enrichment slots 2 vs 3); a free candidate edit makes them agree; any edit that adds a contradiction is rejected automatically; the A/B engine decides whether it ships. We report that verbatim loops are rare (about 1.7% of calls), so the fix is a safety measure and a one-point effect needs about 83,000 calls to prove.
7. **Browser testing found real bugs:** an interval that contradicted a decision (fixed by inverting the same score test), controls rebuilt every animation tick, mobile overflow, a long-running status chip that overflowed a phone, a generated demo audio that spoke "[Buyer Name]" aloud.
8. **Credits as a constraint.** Costs are computed before spending: re-tag Rs 23, Sarvam edit draft Rs 0.9, pre-check Rs 116 (the real prompt is about 22,000 tokens per turn), voice arena Rs 53. Nothing was spent after the real prompt arrived.
9. **Scope check, then a results-file path.** The PM said the voice test is not ours and that files with metrics for A and B would come to us. We checked this against the PS05 document, the BRD, the dashboard spec and the event deck instead of assuming: it holds for the first three and is incomplete against the deck (which also lists an LLM call-tagger and a Sarvam voice test bed). So the engine now judges results files (`canary/decide.py`), the voice layer stays optional, and the open question goes to the organisers.
10. **Two more documents, scrutinised not copied.** The dashboard spec's single end-of-test look was measured against our sequential rule on identical traffic (both near the 2.5% false-win budget; the spec's rule catches a clearly worse B 89% vs 98% of the time). Its calculator example was found inconsistent. Hold-for-approval, "how many more leads", config locking and rollback were adopted; a language-model-written summary was not, because a model should not write numbers. The Clean Slate theme was applied after a colour-blind check showed its navy cannot be a chart colour.
11. **Testing found a design flaw before we shipped it.** A test that "results arrive day by day = results arrive at once" failed: the planned maximum had been taken from the amount of data loaded. It is now fixed by the pre-registered config alone. A browser test also found an older Proof-page crash caused by hard-coded base rates.

12. **The UI was rebuilt to the spec.** The PM pointed out that the dashboard differed from the feature spec and the theme. We re-read both (including the spec's flow diagram), rebuilt the dashboard around its eight screens and the Clean Slate layout, built the spec's own demo plan (tests set up and paused on day 2, then "Advance 1 day") plus the BRD's bonus scenario, and kept the earlier technical views as a Tools page. A browser test exposed that approving a history sample did not change the prompt library, which led to giving the bonus scenario its own live test and treating history samples as already settled.

13. **A second BRD arrived (the final version for build), and we scrutinised it instead of copying it.** Most of it matched what we had (one winner call at the end, a 99.9% daily harm check, lead-level analysis, goals and guardrails). The gaps were real: segments, a stratified router with a balance check, goal cards, whole-week durations, a pre-launch checklist, drafts, the full Overview and the post-promotion holdback; all were built. We checked its numbers before using them. Its "false winner about 5%" is the two-sided total (2.5% promoted + 2.5% logged as a loss: measured 2.5% and 2.2% over 12,000 runs); its 1,000-lead minimum would stop the daily harm check from ever starting at a 10% share in a 7-day test (the calculator now warns); and the data has no lead variables, so they are synthetic and labelled. We did not use a language model to read segments (credits; a rule-based reader showed its exact rule, and the New Experiment overhaul later replaced it with a list-based builder). Testing found one real flaw on the way: the by-call share counted out-of-segment calls and showed 13.6% for a 30% split; fixed and tested.

## Tools
Python 3 (numpy, scipy, jinja2, standard-library HTTP server), plain JavaScript and SVG for the dashboard (no libraries, no CDN), poppler `pdftotext` to extract the prompt, Chrome headless + puppeteer-core for screenshot and interaction tests, `unittest` (170+ tests with a fake Sarvam client).

## Reproduce
`./run.sh`. Everything in `QA_REPORT.md` is regenerated from code with fixed seeds.

## Skill evaluation (what we measured)
`skill/ab-test-decision/` was tested the way skills should be: realistic requests, run twice by independent assistants (with the skill, without it), each answer graded against fixed statements (`evals/evals.json`, results in `evals/results.json`).

| | With the skill | Without it |
|---|---|---|
| Iteration 1 (4 requests) statements held | 100% | 75% |
| Iteration 2 (5 requests, improved skill) statements held | 100% | 88% |
| Time per answer (mean) | 114 s | 152 s (about 25% slower) |
| Tokens per answer (mean) | 63,000 | 56,000 (about 12% fewer) |

How to read it honestly: the no-skill assistant was already strong on plain judgement (it refused to ship on a day-3 p-value and counted each lead once). The skill added rigour and consistency: the extra data a repeatedly checked test needs, labelling an exploratory plan, engine-backed verdicts, and a fade warning. One request per case, graded by the builder (not blind), so treat the gap as indicative, not exact. One statement was reworded after iteration 1 because it demanded a format (a lead count) when days were equally valid; both readings are in the record.

What the runs taught us (all fixed): a script's help crashed on a percent sign; the baseline instruction contradicted the tool; the data check ignored the test window; records of real files carried "simulated / demo click" wording; the plan tool demanded inputs it did not need; a win that faded was not covered; and the engine could ship on a peak that had since faded (it now holds for a person instead). The automatic description optimiser needs the `claude` command line, which was not available, so the trigger description was written by hand and a 20-query trigger test set was saved (`evals/trigger-evals.json`) for when it is.
